Tests:

* Test 5 (Area calculation) was upgraded to independently verify the geometry via pyproj's WGS84 Geod boundary area (Expected: 12.7726 sq km) and passed within a 0.001 numerical tolerance against the algorithm's EPSG:6933 output.

Notes:
* Area calculation: Converts geographic CRS into an equal-area projected CRS (EPSG:6933) using GeoPandas before calling `.area` to ensure accurate square meter readings regardless of global location.
* Mask values: It is assumed that pixels with a value of `1` represent flood, and all other values (like `0`) represent background/non-flood.
* Synthetic raster: The raster created is explicitly a tiny 10x10 test fixture containing 16 flood pixels, only used for testing the geospatial processing engine pipeline and not for production fake responses.

PART 5A — EXPLAINABLE RISK ENGINE
Status: COMPLETED

Implemented:
- Deterministic risk calculation service
- Four normalized risk factors (0-1 range):
  * Flood severity
  * Building exposure
  * Road disruption
  * Critical facility exposure
- Explicit prototype weights (sum = 1.0):
  * Flood severity: 0.35
  * Building exposure: 0.25
  * Road disruption: 0.20
  * Critical facility exposure: 0.20
- Weighted risk calculation: normalized_risk = sum(factor × weight)
- Risk score scaling: risk_score = normalized_risk × 10 (0-10 range)
- Priority classification with thresholds:
  * LOW: 0.0 ≤ score < 3.0
  * MODERATE: 3.0 ≤ score < 5.0
  * HIGH: 5.0 ≤ score < 7.0
  * VERY_HIGH: 7.0 ≤ score < 8.5
  * CRITICAL: 8.5 ≤ score ≤ 10.0
- Explainable risk breakdown per factor:
  * Factor value
  * Factor weight
  * Factor contribution (value × weight)
- Pydantic schemas:
  * RiskInput: Normalized input values
  * RiskFactor: Per-factor breakdown
  * RiskBreakdown: All factors breakdown
  * RiskAssessment: Complete risk result
- Development API endpoint: POST /api/risk/calculate
- Edge case handling (all-zero, all-maximum, single-factor)
- Input validation (0.0 ≤ factor ≤ 1.0)
- Deterministic output verification
- Floating-point precision handling

IMPORTANT DISCLAIMER:
The weighting scheme and priority thresholds are prototype design
choices for the ASTRA-SHIELD hackathon demonstration. They are NOT
an official disaster-risk standard or government-approved methodology.

Architecture:
    ML / Geospatial services → raw impact metrics
         ↓
    Normalization (upstream services) → normalized factors [0-1]
         ↓
    Risk Engine (this module) → deterministic calculation
         ↓
    RiskAssessment → explainable output

Key Design Decisions:
1. Deterministic calculation for reproducibility
2. Transparent weighted model (no black-box ML)
3. Normalized [0-1] inputs from upstream services
4. Clear separation of concerns (risk engine independent)
5. Explainability prioritized (breakdown included)
6. Development endpoint for testing/integration
7. Comprehensive validation and edge case handling

API Documentation:
- Endpoint: POST /api/risk/calculate
- Input: RiskInput (4 normalized factors)
- Output: RiskAssessment (score, priority, breakdown, weights)
- Swagger includes full descriptions and disclaimer
- Schema validation enforced by Pydantic

Example Calculation:
Input: flood=0.82, building=0.60, road=0.35, facility=0.50
Breakdown:
  - flood: 0.82 × 0.35 = 0.287
  - building: 0.60 × 0.25 = 0.150
  - road: 0.35 × 0.20 = 0.070
  - facility: 0.50 × 0.20 = 0.100
Normalized risk: 0.607
Risk score: 6.07/10
Priority: HIGH

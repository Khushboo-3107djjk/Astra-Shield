PART 5A — EXPLAINABLE RISK ENGINE
Status: COMPLETED

Implemented:
- Deterministic risk calculation service
- Four normalized risk factors (0-1 range):
  * Flood severity
  * Building exposure
  * Road disruption
  * Critical facility exposure
- Explicit prototype weights (sum = 1.0):
  * Flood severity: 0.35
  * Building exposure: 0.25
  * Road disruption: 0.20
  * Critical facility exposure: 0.20
- Weighted risk calculation: normalized_risk = sum(factor × weight)
- Risk score scaling: risk_score = normalized_risk × 10 (0-10 range)
- Priority classification with thresholds:
  * LOW: 0.0 ≤ score < 3.0
  * MODERATE: 3.0 ≤ score < 5.0
  * HIGH: 5.0 ≤ score < 7.0
  * VERY_HIGH: 7.0 ≤ score < 8.5
  * CRITICAL: 8.5 ≤ score ≤ 10.0
- Explainable risk breakdown per factor:
  * Factor value
  * Factor weight
  * Factor contribution (value × weight)
- Pydantic schemas:
  * RiskInput: Normalized input values
  * RiskFactor: Per-factor breakdown
  * RiskBreakdown: All factors breakdown
  * RiskAssessment: Complete risk result
- Development API endpoint: POST /api/risk/calculate
- Edge case handling (all-zero, all-maximum, single-factor)
- Input validation (0.0 ≤ factor ≤ 1.0)
- Deterministic output verification
- Floating-point precision handling

PART 5B — ZONE-LEVEL RISK ANALYSIS
Status: COMPLETED

Implemented:
- Deterministic regular-grid zone generation
- Configurable grid dimensions (default: 4 rows × 4 columns)
- Flood intersection filtering (only cells intersecting flood)
- Partially intersecting cells retained as full grid cells
- Zone flood severity calculation (intersection area / zone area)
- Building exposure per zone (affected / total buildings in zone)
- Road disruption per zone (affected_length / total_length in zone)
- Critical facility exposure per zone (affected / total facilities in zone)
- Integration with existing risk_service.py (no formula duplication)
- Zone risk scores (0-10 scale, same weights as overall risk)
- Zone priorities (LOW/MODERATE/HIGH/VERY_HIGH/CRITICAL)
- Explainable zone risk breakdown (factor values, weights, contributions)
- Highest-risk zone identification and sorting
- Deterministic zone ordering (row-major, Z001, Z002, etc.)
- Zone-level impact counts (affected buildings, roads, facilities)
- Zone development endpoint: POST /api/risk/zones
- Zone Pydantic schema updates
- Fixed circular import between risk.py and zone.py

Zone Generation Strategy:
- Regular deterministic grid over flood bounding box
- Cells retained if they intersect flood polygon
- Zone geometry is full grid cell (not clipped to flood)
- Grid cells ordered left-to-right, top-to-bottom
- Zone IDs deterministic: Z001, Z002, etc.

Zone-Level Metrics:
- Flood severity: (zone ∩ flood) / zone_area (uses EPSG:6933 projection)
- Building exposure: affected_buildings / total_buildings_in_zone (0 if none)
- Road disruption: affected_length_km / total_length_km_in_zone (0 if none)
- Facility exposure: affected_facilities / total_facilities_in_zone (0 if none)

Risk Calculation:
- Each zone receives the same RiskInput schema
- Calls existing risk_service.calculate_risk() 
- Reuses weights, thresholds, and priority logic
- Single source of truth for risk calculation
- Complete risk breakdown included per zone

Zone Output Fields:
- zone_id: Deterministic identifier (Z001, Z002, etc.)
- geometry: Polygon GeoJSON (full grid cell)
- flood_severity: Normalized [0, 1]
- building_exposure: Normalized [0, 1]
- road_disruption: Normalized [0, 1]
- critical_facility_exposure: Normalized [0, 1]
- risk_score: 0-10 scale
- priority: LOW/MODERATE/HIGH/VERY_HIGH/CRITICAL
- risk_breakdown: Per-factor contributions and weights
- affected_buildings: Integer count
- affected_road_length_km: Float value
- affected_facilities: Integer count

API Endpoint:
- POST /api/risk/zones
- Development endpoint (uses synthetic test data)
- Returns: zones (sorted by risk_score desc), total_zones, highest_risk info
- Clearly marked as development use only

PART 6A — END-TO-END ANALYSIS ORCHESTRATION
Status: COMPLETED

Implemented:
- Analysis service orchestration layer
- Complete end-to-end workflow:
  1. Flood mask processing (geo_service)
  2. Building impact analysis (building_service)
  3. Road impact analysis (road_service)
  4. Critical infrastructure analysis (infrastructure_service)
  5. Overall risk calculation (risk_service)
  6. Zone-level risk analysis (zone_service)
- Normalized exposure factor calculation (affected/total handling)
- Unified AnalysisResponse output combining all layers
- API endpoint integration (POST /api/analyze)
- Comprehensive error handling with APIError propagation
- Synthetic test data configuration
- Development workflow verification

Orchestration Architecture:
```
API Route: POST /api/analyze (analysis.py)
    ↓
analyze_synthetic_disaster(MLAnalysisInput)
    ├─→ geo_service.process_flood_mask(mask_path)
    │   └─→ flood_geometry, flood_crs, affected_area_km2
    │
    ├─→ building_service.analyze_building_impact(...)
    │   └─→ affected_buildings, total_buildings
    │
    ├─→ road_service.analyze_road_impact(...)
    │   └─→ affected_road_length_km, total_road_length_km
    │
    ├─→ infrastructure_service.analyze_infrastructure_impact(...)
    │   └─→ affected_facilities, total_facilities
    │
    ├─→ Normalize exposure factors [0, 1]
    │   ├─→ building_exposure = affected / total (or 0)
    │   ├─→ road_disruption = affected_length / total_length (or 0)
    │   └─→ critical_facility_exposure = affected / total (or 0)
    │
    ├─→ risk_service.calculate_risk(
    │       flood_severity=input.severity,
    │       building_exposure, road_disruption, facility_exposure)
    │   └─→ overall_risk_score, overall_priority, breakdown
    │
    ├─→ zone_service.calculate_zones_with_risk(...)
    │   └─→ sorted_zones (by risk descending)
    │
    └─→ AnalysisResponse (complete unified result)
```

Critical Design Principle:
- API route (analysis.py) does NOT directly call individual services
- All orchestration logic isolated in analysis_service.py
- Single responsibility: route delegates to analysis_service
- Service composition and error handling centralized
- Easy to test and maintain

Exposure Factor Normalization:
- building_exposure = affected_buildings / total_buildings
- road_disruption = affected_road_length_km / total_road_length_km
- critical_facility_exposure = affected_facilities / total_facilities
- If total = 0, exposure = 0 (safe division by zero handling)

AnalysisResponse Structure:
- summary: AnalysisSummary
  * analysis_id (from input)
  * disaster_type (from input)
  * location (hardcoded: "Development Test Area (Synthetic Data)")
  * confidence (from input)
  * severity (from input)
  * affected_area_km2 (calculated by geo_service, NOT from input)
- impact: ImpactSummary
  * affected_buildings (count)
  * affected_roads (count)
  * affected_critical_facilities (count)
- risk: RiskSummary
  * overall_risk_score (0-10 scale)
  * overall_priority (LOW/MODERATE/HIGH/VERY_HIGH/CRITICAL)
- zones: List[RiskZone]
  * All zones sorted by risk_score descending
  * Each zone includes breakdown, impact counts, geometry
- timeline: List (empty for Part 6A)

API Endpoint:
- POST /api/analyze
- Input: MLAnalysisInput
  * analysis_id: str
  * disaster_type: enum (FLOOD, CYCLONE, EARTHQUAKE, WILDFIRE, LANDSLIDE)
  * confidence: [0, 1]
  * severity: [0, 1]
  * affected_area_km2: float (IGNORED; calculated by geo_service)
  * mask_path: str
- Output: AnalysisResponse (200 OK)
- Error handling: Catches and re-raises APIError; wraps generic exceptions

Error Handling:
- Upstream APIError propagates through orchestration
- Generic exceptions wrapped in APIError with descriptive message
- Proper HTTP status codes returned (400, 404, 500)

PART 6B — REAL ML INTEGRATION
Status: COMPLETED

Implemented:
- ML adapter service: backend/app/services/ml_integration_service.py
- Severity normalization from ML [0, 10] scale to backend [0, 1]
- Unique analysis ID generation

- Binary segmentation mask conversion to georeferenced GeoTIFF
- CRS and transform preservation from source image metadata
- Conversion from ML output to backend MLAnalysisInput contract
- No-disaster handling for "normal" ML outputs
- Upload-driven workflow endpoint: POST /api/analyze/image

Architectural Decision:
- The backend geospatial calculation engine remains the source of truth:
  * ML severity is normalized for contract compatibility
  * ML area is not trusted; affected_area_km2 is recalculated by geo_service
  * Flood mask becomes a real GeoTIFF with spatial metadata before downstream analysis
  * Risk, impact, and zone logic remain deterministic and backend-owned

Workflow:
- Upload GeoTIFF image
- Validate CRS and transform metadata
- Run ML classifier + segmentation inference
- Extract binary mask and normalize severity
- Write georeferenced mask GeoTIFF in backend/generated_masks/
- Convert ML result to MLAnalysisInput
- Invoke the existing backend analyze_disaster workflow
- Return the unified AnalysisResponse

Key Validation Rules:
- Severity clamp behavior: values slightly outside [0, 10] are clamped to range
- Invalid values outside safe tolerance still raise ValueError
- Mask must be a 2D numpy array of uint8 values
- Source raster must include CRS and transform metadata
- Unsupported disaster types raise ValueError
